## What shipped (1) — row-level CSV export (`2b89bd7`, merged `61dca03`)

`/reports` is pre-aggregated: `get_call_log_stats`, `get_call_log_by_agent`,
`get_call_log_hourly`. By the time it renders, the interesting questions have been answered away,
so every new question means a new report view. The export ends that treadmill — one row per call,
let the analyst aggregate.

New `rinq/api/export_routes.py`, registered from the bottom of `api/routes.py` in the same
`register(bp)` style as `transfer_routes`:

| Endpoint | Auth | Contents |
|---|---|---|
| `/api/export/calls.csv` | `login_required` | One row per call leg from `call_log` |
| `/api/export/queue-calls.csv` | `manager_required` | One row per queued caller from `queued_calls` |
| `/api/export/data-dictionary.md` | `login_required` | Column meanings + counting rules |

Two files because the metrics live in two tables — `call_log` has **no wait metric at all**, so an
agent-performance export alone can't answer "how long are people holding".

Row generators are in `database/call_log_mixin.py` (`iter_call_log_export`,
`iter_queued_calls_export`) and stream via a generator rather than building a list, so a year of
watson volume never lands in memory. Buttons on `/reports` carry the currently selected period.

### Scoping was inline and is now shared

The admin/manager/`reports_to` cascade lived inside the `/reports` route body. Extracted to
`resolve_visible_emails()` in `services/reporting_service.py`; both the dashboard and the exports
call it. A scoping bug in two places eventually hands a regular user the whole company's call data.

One behaviour change while in there: **an empty team list now matches nothing rather than falling
through to no filter.** `_build_team_filter([])` returns an empty clause, which as a WHERE fragment
means "no restriction" — the export guards against that explicitly. Same class of mistake as the
caller-ID `[0]` fallback from 2026-07-30: a fall-through that silently means "everything".

### PII is off by default

Customer names, emails and phone numbers are withheld unless an admin passes
`?include_customer=1`. Nothing in agent performance, queue wait or hour-of-day analysis needs them.
Every row instead carries `customer_ref` — a per-tenant salted SHA-256 of the caller's **last 9
digits**, reusing the rule `get_call_history_by_phone` already uses so `+61412345678` and
`0412345678` are one person. Repeat-caller analysis survives with no PII in the file, and both CSVs
join on the ref.

The first cut hashed all digits and my own test caught it: `+61412345678` and `0412 345 678`
produced different refs, which would have split one caller in two.

### `queue-calls.csv` is manager-only on purpose

It's deliberately unscoped by agent. Abandoned calls have no `answered_by`, so an agent filter
would drop exactly the rows that make the dataset worth having — the export would report a zero
abandon rate rather than an honest one. Rather than ship a half-scoped dataset that lies, it's
gated on `manager_required`.

### The data dictionary is load-bearing

Three things make this data wrong-but-plausible if you don't know them, so the rules ship with the
file rather than living in someone's head:

1. **Transfer rows are not separate calls.** `_credit_conference_participants()` writes an extra
   `call_type='transfer'` row per additional agent, linked by `parent_call_sid` (gotcha 29). A
   naive `COUNT(*)` inflates call volume by the number of warm transfers.
2. **Timestamps are UTC, the business day is Sydney.** Every timestamp ships in both forms; a 5pm
   spike otherwise lands at 6am.
3. **`talk_seconds` is null on unanswered calls.** SQL `AVG()` ignores nulls; pandas and
   spreadsheets may not.

Also: streams, refuses ranges over 366 days, writes an `activity_log` row naming who exported what.

## What shipped (2) — deleted the dead Admins card (`0ba9915`, merged `ee55785`)

Rinq had **two** role stores, and only one counted:

| Store | Written by | Read by |
|---|---|---|
| `permissions` (tenant DB) | `/admin` Admins card | One line — `web/routes.py:347`, to draw that same card |
| `tenant_users.role` (master DB) | `/admin/users` | `get_current_user()`, i.e. every `is_admin` / `is_manager` check |

A closed loop. It stored a value, displayed it back, and granted nothing. `db.get_permission(email)`
— the singular lookup you'd need to actually check a role — had **zero callers anywhere**.

History: `95698c8` (2026-04-08) added the `permissions` table as the first local replacement for
Watson's Grant service, still carrying Grant's interface down to the hardcoded `'tina'` bot
argument. Eight days later `4e125e9` (2026-04-16) moved role storage to `tenant_users.role` and
built `/admin/users`. The first attempt was superseded but never deleted, and it read as
authoritative — "Admins", on the admin page, with a granted-by column showing Derek's email.

Removed the card, its CSS, the `admins`/`available_staff` lookups feeding it, and the
`/admin/admins/{add,remove}` routes — 160 lines. No replacement link needed: the admin grid already
had a **User Roles** tile pointing at `/admin/users`.

Left in place: the `permissions` table and `LocalPermissionService`. They're the `PermissionService`
interface implementation and unpicking the abstraction is a bigger change than this warranted. **If
someone finds them later and wonders whether to wire them up — no.**

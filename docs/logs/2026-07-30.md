# Session Log — 2026-07-30

## Overview

Started as a one-line question — "what caller ID does Carol Hill have set?" — and
turned into removing a class of bug: **outbound caller ID was being decided by
alphabetical sort order.**

Carol Hill (ext 6966) had *nothing* set, so she fell all the way through
`resolve_caller_id()`'s priority chain to a last-resort `phone_numbers[0]`.
`get_phone_numbers()` is `ORDER BY friendly_name`, and watson's friendly names are
bare digits, so `61244094006` sorts first — Carol had been presenting the
**Batemans Bay** number while working in **Wagga**. Nobody chose that; string sort
order did, and it would have changed silently the moment a number was added,
removed or renamed.

Shipped as PR #10, deployed and live-verified.

## Data changes (applied directly to production, live immediately)

Nothing caches these — `resolve_caller_id` reads the DB per call and tenant
records are read fresh per request (no cache in `master.py` or
`tenant/middleware.py`), so no restart was needed.

- **Carol Hill** → `+61269316440` (Wagga Wagga)
- **Jihaad Jones** (ext 6899) → `+61262804443` (Canberra) — the only other person
  on the accidental fallback
- **watson tenant `twilio_default_caller_id`** → `+61262804443` (Canberra). It was
  **empty**, which is *why* the sort-order guess was reached at all.

Both writes guarded on the target being an active tenant-owned number first
(gotcha 3: PSTN caller ID must be owned by the tenant's subaccount).

All 21 active users now resolve at priority 1 or 2, so the new hard-fail path is
unreachable in normal operation.

## What shipped (PR #10, `efcaa56`, merged as `6a258af`)

**There were four independent copies of the priority chain**, each ending in its
own arbitrary "first row" pick. All four `[0]` guesses removed:

| Location | Was |
|---|---|
| `services/caller_id.py:79` | `phone_numbers[0]` |
| `web/routes.py:939` | `phone_numbers[0]` (admin overview) |
| `api/routes.py:4913` | `numbers[0]` — **the live outbound call path** |
| `api/routes.py:5517` | `phones[0]` (queue answer / agent ring) |

Priority 4 is now the **explicit tenant default only**. When nothing resolves,
`resolve_caller_id` returns `caller_id=None` and callers must refuse — documented
in the module and function docstrings.

**Derek's constraint on the hard fail:** "we need to ensure the user knows what
went wrong so they can fix it." A silent hard fail just trades a wrong number for
a dead phone. So the reason is surfaced on every surface it can reach:

- **Desk phone / mobile SIP** — spoken via TwiML `<Say>` then `<Hangup/>`. These
  have no screen, and `/api/voice/outbound` serves browser, mobile SIP and desk
  phones alike (gotcha 12), so one code path covers all three.
- **Browser softphone** — `makeCall()` pre-flights the hidden `#callerId` input
  and shows a **persistent** banner (reused `showOutboundOutcome`, extended with
  `detailOverride` + `persist`) instead of dialling into an audio-only error that
  is heard once and gone.
- **Admins** — `/admin/caller-id-overview` gets a red banner, highlighted rows,
  and "None — calls blocked" in place of a `-`, so it is fixable *before* someone
  dials.
- **Logs** — `logger.error` naming the user and the exact setting to change, plus
  an `outbound_call_refused` activity-log entry.

## Two bugs found along the way

1. **The live outbound path was skipping priorities 2 and 3 entirely.**
   `api/routes.py:4909` checked only `staff_extensions.default_caller_id` and then
   jumped straight to `numbers[0]` — so `can_make` phone assignments and section
   matches **never applied to real calls**, and the "Source" column on the admin
   overview could disagree with what the customer's phone actually displayed. Now
   routed through the shared resolver.

2. **A latency regression this session introduced, then fixed.** Routing the live
   call path through the resolver put priority 3's `get_staff_directory()` lookup
   on every unresolved outbound call. Priority 3 now short-circuits when no phone
   number has a `section` — a match is impossible in that state, so the work is
   pure waste. (Initially described as an HTTP round-trip; the boot log shows
   watson's provider is `local`, i.e. a local DB read. The guard is still correct
   — the provider is pluggable and could be remote — but the severity was
   overstated at the time.)

## Display fix (so the change is verifiable by the person affected)

Twilio seeds `phone_numbers.friendly_name` with the number's own digits, so Carol
would have read "Calling as **61269316440**" and been unable to confirm anything.
Both `resolve_caller_id`'s display builder and `web/routes.py::_number_display`
now treat a name whose digits equal the number as *no name*, and fall through to
the `verified_caller_ids` label — where the office names actually live. Carol now
reads "Calling as **Wagga Wagga**".

## Rejected: reviving section-based caller ID (priority 3)

I offered this at the end and then recommended against it after investigating.
**Do not re-attempt without new information.** It is dead on *both* sides, so a
data backfill alone cannot fix it:

- `phone_numbers.section` is blank on all 8 watson numbers (nothing to match)
- watson's staff directory provider is `local`, and
  `LocalStaffDirectory._ext_to_staff()` (`integrations/local/staff.py:18`) returns
  **no `section` key at all**; `get_sections()` returns `[]`. So
  `staff_data.get('section')` is always `None` and the branch can never fire.

And the payoff is zero even if both were fixed:

- only **5 of 21** active staff have a section in `address_book` (Carol and
  Jihaad, the two who needed it, have no row at all)
- of 13 distinct section values only 3 are offices (Shoalhaven, Batemans Bay,
  Wagga Wagga); the rest are departmental — Senior Management, Commercial,
  Production, Purchasing, Wholesale, Designer Drapes, Customer Success…
- all 5 staff who *do* have a section are in non-geographic ones and already
  present Canberra correctly, so nothing would change for them

The onboarding gap it was meant to close is already covered: the new admin flag
surfaces an unset caller ID in red as soon as a new starter appears, and the
Canberra tenant default means nobody is ever blocked meanwhile.

**If auto-defaulting new starters is still wanted**, use
`staff_extensions.reports_to` instead — that column is populated and already
drives recordings/reports visibility, so inheriting a manager's caller ID would
actually work where sections can't.

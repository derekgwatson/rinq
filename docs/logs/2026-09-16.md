# Session Log — 2026-09-16

(Ran into 09-17; PRs #13 and #14 merged on the 17th.)

## Overview

Started as a support question — Clare couldn't find Phil Fenech's calls with a Nowra customer in
Tina, and asked whether she was missing a permission. She wasn't; she's an admin and sees
everything. The calls were there. What wasn't there was any recording of them, or any name
attached to them.

Both turned out to be the same root cause wearing two hats: **recording and outbound attribution
were both written only for the browser softphone**, so everyone on a SIP device — a desk phone or
a softphone app, Rinq can't tell the difference — fell through silently.

Four PRs, all merged and deployed. The last two surfaced from checking the first two: changing a
greeting's wording took seven steps and the obvious first step did nothing, and deleting a recording
a call flow was using stranded it silently.

## The measurement that framed it

`call_log` can't say which device someone uses — it stores the office number. Twilio's own records
can, via the `client:` / `sip:` identity on the leg that **answered** (or placed) a call. Ringing
proves nothing: both legs ring on every inbound call.

Over 21 days, staff were **100% one or the other**, never mixed:

## What shipped (1) — record all calls server-side (`4d8419d`, merged `f257561`, PR #11)

Recording was started by JavaScript in `phone.html`, so it ran for exactly the call paths that run
that JavaScript. It now starts from the Twilio webhooks that fire however a call was answered:
`conference_join` (inbound) and `outbound_customer_join` (outbound).

Both record the **customer's** leg, which outlives agent legs through transfers.
`customer_leg_for_conference()` in `services/recording_service.py` maps a conference name to that
leg, and declines mid-call rooms (`hold_`, warm-transfer consult) where recording is already
running on a leg that survives the move.

Gated by the per-tenant `bot_settings` flag `record_all_calls`, **default off**. While off nothing
changes — the browser keeps auto-recording per each user's preference — so switching it on couldn't
cost the ~10 browser users their existing coverage. Derek switched it on **2026-09-16 05:17 UTC
(15:17 Sydney)** at Admin → Storage.

Supporting pieces:

- **Migration 080** adds `recording_starts`: an atomic per-leg claim (`INSERT OR IGNORE` on a
  PRIMARY KEY). gunicorn runs 3 workers and several webhooks can reach the same conversation, so
  the guard has to be in the database. A failed Twilio call releases the claim so the next
  participant retries rather than leaving the call permanently unrecordable.
- `start_recording()` now returns a recording already in flight instead of creating a second.
  Twilio will happily record a leg twice — bills twice, files two rows, plays back as duplicates.
- start/stop/status resolve whichever leg the caller knows about to the leg actually carrying the
  recording, so the browser Record button still works when the server recorded the customer's leg.
- The recording-status webhook takes conference and call type from its own callback URL when
  present. Its fallback derives them from the conference-name prefix, which reads a **direct
  inbound** call as outbound because both sit in a `call_<sid>` room. The hint is validated
  against known call types — that webhook is unauthenticated.
- Call type prefers the leg's logged `direction` over the caller's hint, because `conference_join`
  is also reached mid-call when a customer comes back off hold.
- Admin toggle at `/admin/storage`; the recordings and phone pages stop offering a personal switch
  the company setting has overridden. The 5-minute cleanup cron drops spent claims.

## What shipped (2) — SIP outbound attribution (`230c9ec`, merged `c7839d6`, PR #12)

Turning recording on made the second half louder: the new recordings were filed under **nobody**.

`voice_outbound` only recognised browser identities (`client:user_at_domain`). A SIP device arrives
as `sip:<username>@…`, fell through, and left `staff_email` as `None` — which the call log, the
conference participant record and therefore the recording owner all inherited.

So a desk-phone user's calls were unsearchable by name, and because `/recordings` filters by staff
email for non-managers, **they couldn't see their own recordings**. Only an admin could, listed
against no one. That is exactly what Clare hit.

The answer was already in the function: caller-ID resolution did its own `sip:` → email lookup
into a local **three lines above** the `log_call` that ignored it. That copy is gone; identity is
resolved once, at the top, before any branch needs it.

Verified on prod data that all three affected users map cleanly, and that no user row is missing a
username or staff email. An unknown SIP device still resolves to `None` — nameless is correct,
mis-attributed is not.

Two side effects, both in the intended direction: SIP presence is stamped on every outbound SIP
call rather than only those placed without an explicit CallerId; and an extension call from a desk
phone now reaches the receiving browser as that person's identity, so it shows their name — which
is what the `caller_identity` line was written for.

Inbound was already attributed (the ring path knows which agent it rang). This was outbound only.

## What shipped (3) — re-record audio in place (`c7558d1`, merged `2bc7e2b`, PR #13)

Found while telling Derek how to add a recording notice to the greetings. The instruction was
wrong, and it had already bitten: he edited the Batemans Bay greeting's text at 06:07 and the
audio never changed.

The Edit form's *Spoken Text* box only wrote `tts_text` — a caption — and
`_AUDIO_FILE_UPDATE_COLS` excluded `file_url`/`file_path`, so **no edit to that box could ever
change what a caller heard**. It just left the stored words describing audio that said something
else, with nothing on screen indicating a problem.

Actually changing a greeting meant: copy the wording out, scroll to the separate TTS form, paste
it, re-pick provider/voice/stability (none of it carried over), preview, save — which minted a
**brand new file and record** — then go to Call Flows and re-point the greeting at it, leaving the
old one in the list forever. The button labelled "Regenerate" opened that create-new form.

Now there's a **Re-record** button per generated file, prefilled with that recording's own words,
voice and style. Preview, then Save & replace writes the audio onto the **same record**, so every
call flow and number already pointing at it keeps working and no orphan is left behind.

Details that matter if this is ever touched again:

- `replace_audio_content()` writes the sound and the words that produced it in one statement, so a
  record can't claim to say something it doesn't. `update_audio_file()` still can't touch the file,
  deliberately — splitting those two is what let them disagree.
- **A new filename every time.** Overwriting would leave Twilio and browsers serving whatever they
  cached at that URL, so the greeting would keep saying the old thing while the screen insisted it
  had changed.
- The superseded file is deleted only after the record points elsewhere, and only when no other
  record points at it. Cleanup failure never fails the re-record.
- Re-record uses the voice that recording was **made** with, not the current tenant default —
  otherwise changing words to one greeting quietly changes who says it, and the four office
  greetings stop sounding like the same person. `voiceFor()` resolves this once for preview and
  save, so what you hear is what gets stored.
- Preview reuses `previewTTS()` untouched by matching its element-id convention. The two
  hand-copied edit forms (per-flow sub-rows, single-file types) are now one Jinja macro — they had
  already drifted apart.

## Decisions

- **Shipped the recording flag off** and let Derek switch it on, because turning it on is the
  moment every customer is recorded and the greetings needed the notice first.
- **Kept the per-user preference alive as the fallback** while the flag is off, rather than
  retiring it outright as originally proposed. Retiring it immediately would have stopped recording
  for the browser users already covered.
- **Recorded the customer's leg, not the agent's**, so a transfer doesn't end the recording.
- **Call-leg recordings, not Twilio conference recordings.** The downstream pipeline has 29,093
  call-leg rows behind it; the webhook's conference branch had produced exactly **1** row ever.

## What shipped (4) — audio delete guard (merged PR #14, 2026-09-17)

Found by checking whether the greetings had actually taken. Three had; Batemans Bay hadn't, and the
reason was a bug the re-record work hadn't touched.

Deleting an audio file only sets `is_active = 0`, but the runtime reads the row regardless — so a
deleted recording **keeps playing to callers** while disappearing from every admin list. And the
call-flow dropdowns list active files only, so the flow pointing at it renders as **"None
selected"**: the next save of that flow, for any unrelated reason, writes NULL and the greeting goes
silent.

Batemans Bay hit exactly that. On 2026-09-16 the old audio interface forced
generate-new-then-delete-old, leaving flow 1 pointing at deleted record 5 (January audio, no notice)
while the correct record 45 sat unreferenced. Callers heard the old greeting for a day; anyone
checking the admin page heard the new one — which is why it survived two people looking at it.
Derek repointed the flow by hand.

⚠️ **Worth being explicit about how close this came to worse.** Opening that call-flow screen showed
no greeting selected. One save, for any reason, and Batemans Bay would have had no greeting at all.

Two guards:

- `delete_audio` refuses while any **active** call flow references the file, naming the flows and
  which slot each uses (`Batemans Bay (greeting)`). A flow that is itself inactive doesn't block it.
- The call-flows screen adds deleted-but-referenced files back into the dropdowns, flagged
  `DELETED RECORDING, pick a replacement`, with a banner linking the audio so you can hear what
  callers actually get. Keeps the value selected so saving preserves it. Nothing should reach this
  state now — it's the net.

The slot list comes from `PRAGMA table_info(call_flows)`, not a hardcoded tuple (which only supplies
readable labels), so a seventh `*_audio_id` column added by a later migration is guarded
automatically — the same list-that-goes-stale shape as the bug itself.

Verified against a rebuild of the exact Batemans Bay state, with a mutation check confirming that
dropping a column from the list would let that slot's recording be deleted, and a simulated future
migration confirming an unknown column is guarded with no code change.

## Notable discoveries

- **Browser vs SIP is the split that matters**, and it's near-total per person. Rinq cannot
  distinguish a desk phone from a SIP softphone app — both are just SIP.
- **Anything built in `phone.html` covers only the browser half and fails silently.** That's the
  general lesson behind both bugs. If a feature must cover everyone, hook a server-side webhook.
- **`call_log` can't tell you someone's device**; Twilio's own records can.
- **A route decorator silently attaches to whatever function follows it** — inserting a helper
  between `@web_bp.route('/admin/audio')` and `admin_audio` hijacked the route. Caught before
  shipping; an `ast` check now asserts no route decorates a private function.
- **`tts_text` is not evidence of what callers hear** for anything edited before 2026-09-17.
- **The screen and the caller can disagree, and did twice in two days** — once from editing text
  without re-recording, once from deleting a file still in use. Both now guarded, but when checking
  audio, resolve it through the CALL FLOW rather than trusting the list.

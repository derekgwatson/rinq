# Session Log — 2026-10-07

## Overview

Queue auto-ring was only ever ringing SIP and browser legs. Mobile forwards were configured in
staff settings (and being used by at least Michael Dodd on the Shoalhaven queue since 2026-08-06)
but were never dialled by the queue system—only picked up for direct calls, extensions, and
transfers. Root cause: `_ring_agents_for_queue` (rinq/api/routes.py) called `_build_dial_targets`
only for its own staff details list, never checked the `forward_to` field that lives in the
`staff_extensions` table. That morning (2026-10-07) Shoalhaven had **4 of 7 calls abandoned/missed**,
and Michael reported diversion to his mobile wasn't working.

Commit d5ba605 landed on main at 13:47 Sydney and deployed via GitHub Actions. The rinq service
restarted, health check returned 200, and the new `/api/voice/mobile-screen` endpoint is live.

## What shipped

**Queue auto-ring now dials every active, non-DND member's `forward_to`** (if set) using the queue's
own caller ID (`our_caller_id`), tagged `device_type='mobile'`. Each mobile leg immediately enters
a **press-1 screen**:

- GET `/api/voice/mobile-screen` — Gathers one DTMF digit with Twilio's `<Gather>`. Plays
  `<label>. Press 1 to answer.` twice, timeout 4 seconds, else hangs up.
- GET `/api/voice/mobile-screen/accept` — On Digits=1, a relative `<Redirect>` to the caller-supplied
  `next` parameter (must start with `/api/voice/`, no `//` or backslash).

**Every mobile leg is screened** — queue, direct calls, extension rings, internal extensions:
- New `db.get_staff_email_by_forward_to(number, tenant)` resolves mobile numbers to staff emails
  for attribution.
- Queue-answer path: accepts new `agent_email` query param for mobile legs (the `Called` field on
  a mobile ring is just the number). `queue_agent_answer` POST extracts it and passes through;
  `queue_agent_ring_status` treats a mobile 'completed' still tracked as a ring-out, and a mobile
  'busy' as ring-out not rejection (queues with `voicemail_on_no_answer` won't trip on a mobile
  on another call).
- Inbound: new `/api/voice/inbound/screened-answer` claims the answer via `_claim_inbound_answer`
  with `require_pending=True` (only 'pending' offers, no 'in-progress'); atomic pop means a late
  press after another leg answered or after the caller hung up loses and is told so. Callback
  includes `screened=1`, and `inbound_ring_status` ignores 'in-progress' for that path.
- Direct/extension calls: mobile status callback carries `screened=1`; no special handler needed,
  the existing flow checks for it.

**Transfers deliberately NOT screened** (yet): `transfer_service` uses literal `<Dial><Number>`,
and Twilio SDK docs don't state whether a `<Number url>` screen keeps sibling legs ringing until
it completes. A live test on the derek tenant first.

## Decisions

**Press-1 screening** over Twilio answering-machine detection (AMD):
- AMD adds latency to every call and historically misidentifies humans as machines.
- DTMF is synchronous and immediate — if a human is on the other end they can hit 1 before it rings twice.
- Derek approved, including applying it to all mobile calls (queue, direct, extension), not just queue.

**Transfers not screened** — flagged but deferred pending live test. It is a safe change to defer:
- The system has been ringing mobiles *somewhere* (direct calls) all along, just not in queues.
- A transfer to a screened mobile is the rarer path.

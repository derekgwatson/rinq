## How to reproduce this on the live system

Test Queue id 8 (only derek active) via +61756258180 (Test call flow → queue 8).
Temporarily raise the queue's "send to voicemail after N music plays" from 1 to
~10, or callers get dumped after ~1 minute.

1. SIM 1 calls. **Let the browser ring fully time out (~30s)** — the caller stays
   parked because `voicemail_on_no_answer=0` on this queue.
2. SIM 2 (a **different** number) calls; the browser rings for SIM 2.
3. Click SIM 1's row — the parked one, not the ringing one.

The ring-out gap in step 1 is essential (see issue #2 below). The two callers
must have different numbers; the fix deliberately falls back to the clicked row
when the numbers are identical or ambiguous. A dual-SIM mobile works as both
callers.

## New bug found — `busy` treated as human rejection (issue #2)

In `api/routes.py` (agent ring-status handler, ~line 2456):

```python
rejected = call_status == 'busy'
```

Twilio returns `busy` for a Client leg that is **already ringing for another
call**, which is not the same signal as a human pressing decline. The rejection
branch then ejects the caller to voicemail if no other agent leg remains ringing.

Observed live: a second caller entering Test Queue while the only active agent's
browser was mid-ring was ejected to voicemail after **3 seconds**
(`Agent derek rejected and no agents remain`, queue leave `result=redirected
time=3s`).

Masked in queues with several active members (Canberra has 6) but **live** for
thin queues: Batemans Bay has 1 active member (chris.savage), Wagga and
Shoalhaven 2 each. No config escape exists — `reject_action='voicemail'` ejects
immediately and `'continue'` still ejects once no legs remain.

Filed as GitHub issue #2, unscheduled.

## UX follow-up — Answer buttons on non-ringing rows (issue #3)

While a ring is pending, the queue list still shows an Answer button on
non-ringing rows. Clicking one connects you to the ringing caller regardless.
Post-fix the UI is now honest about who you got, but it's still confusing.

Proposal: while a ring is pending, only the ringing caller's row shows Answer;
when no ring is pending all rows keep their button (that path genuinely answers
the clicked caller via `AnswerCallSid`).

**Load-bearing safety rule:** whenever the ringing row cannot be identified
(withheld caller ID, two waiting callers sharing a number, a ring for a caller
not in the list) it MUST fall back to showing all Answer buttons. Locking an
agent out of answering is far worse than the confusion being fixed.

Filed as GitHub issue #3, unscheduled.

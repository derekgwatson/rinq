## Decisions and WHYs

### The bug is in Clara, not Rinq — and a refresh would NOT fix it
The number `0456477779` is Edward Hallett's real mobile (Clara customer 137141, clean value, `is_primary=1`). It *also* appears on Michael Weaver's record (customer 112741) as a **malformed contact value**: `0456477779 - Edward ( Tenant )` — a name typed into the phone field during Buz sync (`source=buz_canberra`). Edward is Michael's tenant. Clara's `/api/customers?q=<number>` (`clara/database/db.py` `search_customers`) matched both via substring `LIKE` and ordered only by `updated_at DESC`. Michael synced 3 seconds later → sorted first → Rinq's `find_by_phone` (`integrations/watson/customers.py`, `limit=1` + `customers[0]`) got Michael. Rinq faithfully displayed what Clara handed back.

### Distinct from the just-pulled Rinq race fix (2d2583a)
The session started by pulling `2d2583a` ("stop a concurrently-ringing call's customer details landing on the panel"). That fixes a **different** bug — a non-answered concurrent ring's lookup landing on the panel during the call you *did* answer. Its tell: **panel number ≠ active-call number**. Britt's case had **panel number == active-call number** (both `0456477779`), proving the lookup was correctly scoped and Clara returned the wrong person *for that number*. So no amount of refreshing helps — confirmed via `renderCustomerContext` (phone.html:3360), which renders the call's number, not the customer's stored number.

### Chose Option B (fix in Clara) over Option A (Rinq-side re-rank)
Two viable fixes were identified: (A) Rinq asks for `limit=5` and prefers the candidate whose `primary_phone` digit-matches the number — contained, no cross-repo change; (B) fix Clara's search ranking — proper, fixes it for every Clara consumer. Derek: *"let's just do B... I'm always more inclined to just get the proper fix done."*

### Ranking design
For phone searches only, rank by match quality via a correlated subquery: exact (separator-stripped) hit on a **primary** contact = `0`, exact on a secondary contact = `1`, mere substring hit in a malformed value = `2`; ties fall back to `updated_at DESC`. Name/email searches unchanged. The malformed value strips to `0456477779Edward(Tenant)` ≠ `0456477779`, so it correctly scores `2` while Edward's clean primary scores `0`.
